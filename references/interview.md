# Guided creative interview

Ask **only questions whose answers materially alter the README**. Infer the obvious from the repository and respect already-expressed preferences. Prefer 1–3 questions per round; offer a recommended option plus a way to describe another preference.

## Initial discovery

1. **Audience and purpose:** Who should understand this README first—new users, contributors, maintainers, evaluators, customers? What should they do after reading?
2. **Main idea:** Which real capability or differentiator deserves top billing? If the source is ambiguous, offer your best evidence-backed summary for confirmation.
3. **Identity:** Preserve an existing logo, palette, typography or product tone? Or explore a new visual identity?
4. **Presentation:** Is the preferred approach minimal, editorial, product-first, developer-focused, expressive or something else? Show concrete 2–3 alternatives rather than abstract adjectives.
5. **Visual media:** Which authentic screenshots, demos, diagrams or brand files may be used? May the agent capture new real screenshots, create SVG diagrams or generate conceptual illustrations?
6. **Content:** Which sections are mandatory or excluded? Is a short landing-style README or extensive technical guide the priority?
7. **Language:** Follow repo language or choose a target language? Only ask when ambiguous.

## Approval card for every direction

Present 2–3 compact cards with:

- Name and unique design concept.
- Mood, color/typography, expected top section and real/proposed visual assets.
- First-five-seconds product message.
- Strength and honest cost/limitation.
- Visual preview if possible (concept labeled; never claim it is an actual screenshot).

Ask: **Which direction do you approve, or what would you change?**

**Do not touch README.md or add final assets until approval.** If the user requests changes, refine the options and ask again. Once approved, implement without repeatedly reopening already-settled decisions unless new evidence conflicts.

## Common blockers

- **No source checkout:** Ask for a repository URL, accessible files, or a factual product brief. Do not pretend to have inspected it.
- **No screenshots:** Recommend verified text/CLI examples or a simple diagram; explain limitations. Avoid imaginary UI.
- **Unimplemented features:** Exclude or label as roadmap only when clearly present and approved.
- **Conflicting instructions:** Highlight the conflict and ask which requirement controls.
- **Pure review request:** Skip the implementation gate and provide actionable findings.
